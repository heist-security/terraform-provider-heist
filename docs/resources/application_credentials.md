# heist_application_credentials (Resource)

The credentials an application uses and their privilege order, which Heist uses for authorization testing. The first `tenant` block is the main tenant, which holds the primary credential; each later block is a separate tenant. The resource is authoritative for the application's direct credential links: links made outside Terraform show up as a diff and are removed on apply. Destroying it unlinks every credential from the application, keeping the credentials.

Use one resource per application. Credentials inherited from a parent application aren't links on this
application, so they aren't managed or shown here.

## Example Usage

```terraform
resource "heist_application" "app" {
  url = "https://app.example.com"
}

variable "passwords" {
  type      = map(string)
  sensitive = true
}

# Test accounts in two tenants. create_before_destroy links a replacement
# credential before the old one is deleted, so the main tenant keeps its
# primary credential.
resource "heist_credential" "account" {
  for_each = toset(["acme-admin", "acme-member", "globex-admin"])

  type      = "BASIC"
  login_url = "https://app.example.com/login"

  basic {
    username            = "${each.key}@example.com"
    password_wo         = var.passwords[each.key]
    password_wo_version = 1
  }

  lifecycle {
    create_before_destroy = true
  }
}

resource "heist_application_credentials" "app" {
  application_id = heist_application.app.id

  # The main tenant. Its first credential is the primary.
  tenant {
    credential_ids = [
      heist_credential.account["acme-admin"].id,
      heist_credential.account["acme-member"].id,
    ]
  }

  # A separate tenant, for testing access across tenants.
  tenant {
    credential_ids = [heist_credential.account["globex-admin"].id]
  }
}
```

## Tenants

Each `tenant` block lists credentials most privileged first. The first block is the main tenant, and its first
credential is the application's primary credential. Each later block is a separate tenant, which Heist uses to test
access across tenants. Heist keeps no order between tenants, so reordering the blocks after the first changes nothing.

Blocks are matched to existing tenants by the credentials they share, not by position. A later block joins the
tenant it shares the most credentials with, and a block that shares none starts a new tenant. Removing or reordering
blocks therefore doesn't move credentials between tenants. Moving a credential to another block unlinks it and links
it again. `entity_id` shows Heist's ID for each tenant and is informational.

## Replacing credentials

Set `lifecycle { create_before_destroy = true }` on `heist_credential` resources referenced here. Terraform then
links a replacement credential before deleting the old one. Without it, replacing the only credential in the main
tenant deletes it first, Heist moves the primary to another tenant, and the next apply fails as described below.

## Primary credential in the wrong tenant

The API can't move the primary credential between tenants. If the primary leaves the tenant that the first block
manages, for example because that tenant's last credential was deleted, plan warns and apply fails. To recover,
replace the resource:

```shell
terraform apply -replace=heist_application_credentials.<name>
```

Replacing it unlinks every credential, then links the first block's credentials first, so the first credential
becomes the primary.

Alternatively, accept the tenant that now holds the primary as the main tenant: put one of its credentials in the
first block, and apply.

## Import

Import is supported using the following syntax:

```shell
terraform import heist_application_credentials.app 8b1f4c2e-5a3d-4e6f-9c7b-2d1e0f3a4b5c
```

Import reads the application's direct links: the tenant holding the primary first, then the other tenants. The
tenant holding the primary becomes the main tenant, so apply fails if the primary later leaves it.
